## Assumptions

- **A1 [unsupported]:** future consumers will need a substantial fraction of Ant/Ant X capabilities beyond Platform's present screens. Platform being the *first* consumer supports investigating this, not the demand estimate (`CLAUDE.md:6`).
- **A2 [unsupported]:** repeatedly discovering, composing, documenting and fixing missing convenience surfaces costs more across consumers than maintaining packaged versions once. No measured cost comparison was supplied.
- **A3 [unsupported]:** representative consumers can provide import/prop usage evidence and migration cooperation. I have not established that telemetry exists. Non-observation is not proof of non-use.
- **A4 [unsupported; necessary policy counterfactual]:** the owner would permit a narrow exception to GATE 0/no-duplication for upstream-defined convenience surfaces. Current rules expressly deny this (`docs/COMPOSITION-VS-COMPONENT.md:3–8,32–42`). Without A4, C cannot win eligibility.
- **A5 [proposal]:** pin the currently inspected upstream surface: Ant docs display 6.6.3 and Ant X 2.9.0. This is a documentation baseline, not a verified package-lock version ([Ant overview](https://ant.design/components/overview/), [Ant X overview](https://x.ant.design/components/overview/)).

## Toulmin case

**Claim.** A near-complete, centrally maintained Ant-shaped capability surface is the strongest way to make “available in this library” predictable for a consumer, if A1–A4 hold. Coverage determines the build commitment; present usage determines sequence and later pruning, not admission.

**Grounds.** `TreeList` accepts only `items` and maps them to flat list rows with depth and `aria-current` (`src/components/data-display/tree-list.tsx:14–38`). `BadgeProps` offers status/color/shape but no count or removal contract (`src/components/data-display/badge.tsx:99–134`). Meanwhile `Tabs` already implements editable items and controlled selection (`src/components/navigation/tabs.tsx:155–208,278–365`), and DataTable explicitly accepts Ant-shaped pagination plus row-selection/expansion surfaces (`src/components/data-display/data-table.tsx:404–412,462–491`). Breadth is uneven; a familiar component name is not evidence of capability completeness.

**Warrant [inference].** A consumer benefits from a predictable *supported API*, not merely proof that someone could assemble equivalent JSX. C moves that assembly, documentation and regression obligation into the framework. It removes “not needed yet” and “compose it yourself” as ordinary reasons to stop implementing an upstream surface. This specifically addresses discoverability and delivery; it does not prove correctness or prevent regression by itself.

**Backing.** The current specs knowingly leave Ribbon as composition, six AI-related surface rows as compositions/extensions/reuse, and Tree drag/drop plus virtualization out of v1 (`docs/roadmap/badge-tag-chip-count.md:135–140`; `docs/roadmap/ai-chat-components.md:24–38`; `docs/roadmap/tree-components.md:80–82`). These are explicit decisions, not unnoticed omissions. C's argument is that their *packaging cost still belongs centrally*. DataTable's existing Ant-aligned expansion demonstrates that importing substantial surface is already compatible with parts of this architecture; it does **not** demonstrate that copying every surface is cheap (`src/components/data-display/data-table.tsx:462–491`).

**Qualifier.** “Near-complete” means normalized capabilities, not literal Ant prop spellings, CSS internals, server SDKs or unsafe escape hatches. Vocabulary and tokens remain authoritative (`docs/roadmap/antd-parity.md:9–21`). The vocabulary document itself contains older `ButtonSizeProp`/physical alignment entries (`docs/PROPS-VOCABULARY.md:58–62`); the topic's explicit normalized contract governs this proposal, not those exceptions.

**Rebuttal anticipation, preceded by steelman.** The strongest contract objection is correct: centrally packaging a composition duplicates a supported route even if its implementation delegates to existing primitives; publishing it creates another permanent API. The tree spec already forbids deleting TreeList because consumers exist (`docs/roadmap/tree-components.md:117–125`). C's answer is an economic wager under A2: duplication of *surface* can be cheaper than distributed composition ownership. That is a reason to reconsider the boundary, not evidence that the present boundary permits C.

## The four decisions

**1. Scope [proposal].** Systematically port the pinned Ant core and Ant X UI surface, extending existing owners and adding upstream convenience surfaces such as Ribbon, Prompts, Welcome and Sources to `src/components/` under A4. These are the concrete additions that distinguish C from A. Delegate rendering/interaction to Badge/Card/Button/ListRow and other existing primitives; do not fork their engines. The current AI ledger explicitly fails these candidates at multiple criteria, including C2/C3/C4/C6/C7; publish those failures rather than fabricate seven passes (`docs/roadmap/ai-chat-components.md:26–31`). This requires an exception broader than just C3.

Retain house names, controlled triads, logical directions and token geometry; retain Badge's identity. Exclude Ant's obsolete List API in favor of Listy, inline-style twins, arbitrary a11y-bypassing renderTabBar, and provider/service SDK plumbing. The upstream replacement and local exclusions are explicit ([Listy](https://ant.design/components/listy/); `docs/roadmap/list-masonry.md:17–19,52–55`; `docs/roadmap/antd-parity.md:20–21,69`; `CLAUDE.md:6`). These bounded exclusions do not turn composition into a general veto.

**2. Composition boundary [proposal].** The owner, not a coding agent, must decide A4. A single integration reviewer then publishes each candidate's C1–C7 verdict plus the approved exception reference. Under C, membership in the pinned upstream UI catalog creates a presumption of a supported package surface even when composed internally; brand pages/business workflows remain consumer-owned. Until the policy changes, failed candidates cannot enter source. Calling a wrapper “thin” or “experimental” does not pass GATE 0 (`docs/COMPOSITION-VS-COMPONENT.md:32–42,56–66`).

**3. Priority [proposal].** P0 remains demonstrated broken consumer journeys or correctness defects; no speculative feature becomes P0 simply because Ant has it. First complete the already-owned Tree/chat slices. Next fund shared virtualization and missing count/list/masonry behavior; then drain remaining behavior and convenience surfaces, including P2, on a committed schedule. P1 is a risky workaround or reusable prerequisite; P2 is convenience/presentation with no demonstrated blocker. The distinguishing commitment is that P2 stays in the port budget, rather than needing fresh consumer demand. Existing roadmap priorities and the absent virtualization baseline support this ordering (`docs/roadmap/antd-parity.md:38–39,63–94`; `docs/roadmap/list-masonry.md:8–11`). No honest evidence establishes a finish date for the entire port.

**4. Execution this week [proposal].** Keep the three existing writer assignments and three auditors; add no agents. Day 1: freeze upstream scope, obtain exact file ownership acknowledgments, inventory candidate exceptions and obtain the owner's boundary decision. Days 2–4: finish owned Tree/chat work and assign the next complete vertical slice only when its owner is free. Day 5: one integration/acceptance window and an evidence-backed remaining queue. These are planning targets, not throughput measurements (`00-Topic.md:46–51`).

Use exact file leases, not group names: Tree and ChatBubble both touch data-display. One rotating integrator exclusively owns group prop files, registry, catalog, locale JSON, group exports and token imports; writers hand over proposed additions without editing those files. Shared tree/virtualization utilities also have one owner. Freeze participating writers during integration; preserve unrelated diffs. These chokepoints follow the required artifact list (`docs/roadmap/ai-chat-components.md:182–195`) and tree utility sharing (`docs/roadmap/tree-components.md:127–132`). Auditors inspect remaining upstream surface concurrently; their ledger is a delivery checklist, not C's scope authority or D's prerequisite gate.

For subsequent implementation, one scheduler permits one targeted test process with at most two workers; one acceptance runner performs required static checks and Platform browser verification. Full-suite work belongs to CI, with no CI polling loop (`CLAUDE.md:10–13,26`). **This R0 executes no tests/builds/servers and changes only its two assigned debate files.** No browser or accessibility pass is claimed.

## Weakest point, failure condition, pruning

C's weakest point is **irreversible API growth justified by unmeasured future demand**. TreeList must remain exported and Badge cannot be renamed/aliased under the current work (`docs/roadmap/tree-components.md:119–125`; `docs/roadmap/badge-tag-chip-count.md:142–146`). “Prune later” is therefore a migration programme, not deleting unused files. Proposed evidence: opt-in consumer import/prop inventories, usage duration, consumer coverage, migration owner and a compatible replacement. Unobserved consumers keep removal uncertain. Maintain deprecated adapters until migrations are established; no automatic pruning from zero telemetry.

C fails immediately if hard constraints remain unchanged. Even with A4, it loses its economic case if demand is sparse, telemetry is unrepresentative, or the review/behavior-test queue grows faster than accepted slices. Stop widening the exported surface when that happens. The additional contract work is concrete: every candidate brings locale, a11y, registry, catalog and real-screen obligations (`docs/roadmap/ai-chat-components.md:178–195`). Delegating internals cannot erase those costs.
