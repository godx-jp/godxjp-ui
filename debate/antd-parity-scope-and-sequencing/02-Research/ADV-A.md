## The four decisions

### 1. Scope: account for everything; implement only justified behavior

**Proposal:** audit all 127 baseline entries, including explicit “no counterpart” dispositions, and maintain a reverse index of the Ant/Ant X reference surface. A godx-only inventory would miss entirely absent components—the exact problem recorded for List/Masonry and chat (`docs/roadmap/antd-parity.md:47-50`). Compare APIs, defaults, interaction modes, keyboard, responsive behavior, async/error states and documented limitations, not just prop names. Each row gets one of the five statuses, destination, evidence, priority, owner and acceptance link. Uninspected rows remain visibly uninspected; do not count them as PRESENT or WONT-PORT.

Use the existing scope decisions: Tree, CountBadge, List, Masonry and four chat primitives have published seven-criterion ledgers; ConversationList/ThoughtChain remain conditional; attachments extend Upload; code rendering uses CodeBlock; Prompts/Welcome/Actions/Sources are compositions (`docs/roadmap/tree-components.md:43-55`; `badge-tag-chip-count.md:51-63`; `list-masonry.md:21-33,88-100`; `ai-chat-components.md:18-38,157-174`). The [Ant X overview](https://x.ant.design/components/overview/) is a reference inventory, not blanket permission to export its surface.

List means the focused Listy capability set: virtualization/grouping; frame, separators and paging compose existing primitives (`docs/roadmap/list-masonry.md:15-55`; [Ant Listy](https://ant.design/components/listy/)). A deferred capability such as Tree virtualization stays MISSING with a follow-up, not WONT-PORT or CLOSED (`docs/roadmap/tree-components.md:81-82`).

### 2. Composition boundary: author proves; reviewer decides

**Proposal:** the group owner submits all C1–C7 verdicts; an independent framework reviewer verifies them before source addition. Any failure or unresolved criterion means composition. Prior ledgers are starting decisions, not permission to ignore a newly available primitive. WONT-PORT needs a reason in the catalog; COVERED-ELSEWHERE needs links on both sides (`docs/roadmap/antd-parity.md:33-36`).

Do not mechanically copy contradictory documentation: `docs/PROPS-VOCABULARY.md:58,62` still lists `size="default"` and physical alignment; the topic explicitly requires house sizes and logical direction (`00-Topic.md:66-74`). Likewise the StatCard example has borderline C2 (`docs/COMPOSITION-VS-COMPONENT.md:79-86`); it cannot waive the topic's seven-pass rule for new additions. Record the conflict and apply the binding rule. New visual knobs become tokens. This is why semantic review must precede encoding decisions as automatically trusted facts.

### 3. Priority: screen failure first, unsafe workaround second

Use the existing P0/P1/P2 definitions (`docs/roadmap/antd-parity.md:38-39`): P0 requires a cited broken real screen; P1 requires a hand-rolled, accessibility-risky workaround; P2 is optional benefit. Absence alone does not prove P0. No Platform journey was inspected here, so I assert no new P0 finding.

**Proposed ordering:** proven P0s interrupt the queue; finish and accept in-flight Tree/chat work; next drain evidenced P1s, including the roadmap's Tabs overflow and Steps responsive gaps (`docs/roadmap/antd-parity.md:65,81`). CountBadge/removal gets P1 when a concrete workaround is demonstrated. Sequence List before dependent consumers when virtualization is required; otherwise List/Masonry remain recorded work, not automatic emergency projects. Within a priority, prefer shared leverage and smaller reversible changes. This is an ordering rule, not an unsupported estimate of delivery time.

### 4. Execution: ownership must include shared files

The topic's two data-display writers (Tree and ChatBubble) conflict with A's one-writer-per-group rule (`00-Topic.md:48-50,85-90`). **Proposed transition:** preserve all work, let each report its current edits, then queue their remaining writes serially under one data-display owner. The queued writer becomes a read-only reviewer. Data-entry can proceed independently. Existing audit agents remain read-only and work on distinct component sets; each report records the observed source revision.

Group separation alone is insufficient: every public addition touches the shared catalog, registry, token imports and three locale files (`docs/roadmap/ai-chat-components.md:182-195`). Reserve those files to one integration owner. Group owners supply exact proposed hunks; only the integrator applies them. Group prop files, barrels and shared group styles belong to the group owner. Cross-group changes—TagInput consuming Badge, or Tree sharing traversal—queue both affected ownership slots (`badge-tag-chip-count.md:113-116`; `tree-components.md:129-132`). No overlapping file writes, broad staging, cleanup or reset of unrelated edits.

**This week's proposed deliverables:** first establish ownership and consolidate the current audits; then fill coverage holes while accepted groups begin P0/P1 repairs; finish with one reviewable inventory of reviewed/uninspected rows and accepted/open fixes. Do not promise complete parity in a week. During implementation, one validation slot runs relevant tests with at most two workers; batch static checks and Platform browser acceptance, then normal asynchronous CI (`CLAUDE.md:10-13,26`). During this debate, run none. No additional coding agents are needed merely to increase concurrency.
