## The executable artifact

**Proposed shape:** one checked data file with baseline metadata and component/capability rows. Each row contains stable ID; upstream package/version/URL/API path; the five-way status; target component/type/member or token/composition; normalized value/default differences; source symbol and human `file:line` citation; verification state; evidence links; priority; owner; decision reason. Component records also carry inventory completeness. GATE-0 records carry seven verdicts, rationales and reviewer identity.

Separate `status` from `verification: unreviewed | pending | verified | failed`. An API may exist while its behavior is unverified. A missing capability deferred beyond v1 remains MISSING with a milestone; it does not become WONT-PORT just to make totals attractive. A deliberate rejection needs a reason and owner. This implements the roadmap’s measured-gap rule and preserves the tree spec’s explicit v1 deferrals (`docs/roadmap/antd-parity.md:22`, `docs/roadmap/tree-components.md:81`).

**Proposed `check:antd-parity` obligations:**

1. Every key in a separately pinned upstream inventory has exactly one disposition. Include component APIs, nested item types, ref methods and documented behaviors; common inherited props can reference a shared inventory. Missing extraction is an explicit incomplete inventory, never an empty API. Upstream changes enter through a reviewed baseline refresh, not network requests on every CI run. The current List→Listy change demonstrates why baseline identity matters ([Ant overview](https://ant.design/components/overview/); `docs/roadmap/list-masonry.md:17`).
2. PRESENT/RENAMED/COVERED-ELSEWHERE targets resolve through the registry to actual exported component types and catalog entries. Check relevant types/value domains, not only names. The existing API manifest is a starting point, with its documented lower-bound limitations respected; unresolved cases remain unverified, never silently skipped (`scripts/check-doc-prop-existence.mjs:13`, `:25`). Explicit adapters must have fixtures. Use TypeScript symbol resolution where possible; do not copy the regex extractor and assume completeness.
3. Validate coverage destinations and bilateral catalog links; token destinations must reference declared documented tokens; compositions must reference a real showcase. New framework components require seven published PASS verdicts. Machines check the record’s completeness; a maintainer owns its truth (`docs/roadmap/antd-parity.md:34`, `docs/COMPOSITION-VS-COMPONENT.md:32`).
4. Compare against the accepted map: no disappeared rows, silent downgrades, unexplained WONT-PORT additions or vanished destinations. A newly added local prop must update its mapping or receive an explicit local-only classification. Defaults and runtime behavior require evidence beyond the type checker. Changed implementation/evidence invalidates the affected verification record until reviewed and validated; line numbers alone are not stable identifiers.
5. Report separately: inventoried vs unaudited surfaces; acknowledged missing capabilities by priority; API mappings verified; behaviors accepted. Fail structural drift and missing dispositions. A delivery milestone additionally fails its required MISSING/unverified rows. Never advertise “100% parity” because every row has a status.

The checker itself needs small fixtures that remove a mapped field, alter a union, leave an upstream key unmapped, break a coverage link, and exercise an inherited/unresolved type. These are proposed implementation acceptance checks, not tests executed in R0. Actual UI acceptance retains targeted behavior/axe checks and Platform journeys (`CLAUDE.md:10`; `docs/roadmap/ai-chat-components.md:178`).
