# Theme API coverage — an inventory, not a fix

Measured against `main` @ `2ec5fe9a`. This is a count, not a judgement call on any single component; the judgement calls (structural exclusions, alias corrections) are all named below so they can be checked or reverted independently.

## Headline numbers

- **134 components** carry attributable painted CSS in `src/styles/*.css` (out of ~860 catalogued exports — most of the rest are hooks, sub-parts folded into a parent, or non-visual utilities with no CSS of their own).
- **3595 visual declarations** parsed and classified (`color`, `background*`, `border*`, `box-shadow`, `backdrop-filter`, `opacity`, `font-size`, `font-weight`, `letter-spacing`, `padding*`, `margin*`, `gap`, `inline-size`/`block-size`, `min-*`/`max-*`).
- Of the **3073 non-structural declarations**: **2701 reachable (87.9%)**, **372 hard-coded (12.1%)**.
- **522 declarations excluded as structural** (see Methodology) — a separate, itemised judgement call, not folded into the headline percentage.
- **39/134 components measure 100%** of their non-structural declarations reachable through a _published_ token.
- The owner's claim — "every smallest element inside a component must be configurable from the theme API" — is **88% true by declaration count**, concentrated in a **93-component tail**; the worst of that tail (Sidebar, Calendar, Slider, Topbar) sit at 68–78%.

## Method (so the numbers can be checked)

1. **Parsed** every rule in `src/styles/*.css` (22,728 lines) and `src/tokens/components/*.css` (5,771 lines) with a small hand-written CSS tokenizer (no nesting syntax is used anywhere in this codebase — verified by grep — so a brace-depth parser is exact; spot-checked against the source at random for line-number accuracy).
2. **`src/tokens/components/*.css` turned out to contribute zero rows to the classification.** Every rule in it is `:root { --x: value; }` (56 files, confirmed by selector census) — i.e. _custom-property definitions_, not the standard properties (`color`, `background`, …) the brief asks to classify. Its real role here is (a) the source of truth for which `--x` names exist so a `var(--x)` chain can be traced past one hop, and (b) the token-graph inputs for Finding 1 below. Total custom-property definitions found there: **1,688** — which exactly matches `agent/tokens.json`'s `"tier": "component"` count (1,688/1,981), a useful cross-check that nothing was mis-scoped.
3. **Attributed each declaration to a component** by the right-most compound of its selector: `.ui-<name>-…` or `[data-slot="<name>"]`, matched (longest-prefix) against the 860 names in `mcp/src/data/components.ts`. Three real mismatches between the CSS taxonomy and the catalog were found and hand-aliased (not guessed): `.sb-*`/`.tb-*` are undocumented bare-prefix shorthand for **Sidebar**/**Topbar** (no `ui-` at all — a third naming convention alongside `ui-` and `.app-*`); `.ui-legal-document-*`/`.ui-otp-*`/`.ui-auth-account-*` are shorter than their catalog kebab (`legal-document-shell`, `input-otp`, `auth-account-summary`); `.ui-page-header/-toolbar/-footer/-title/-subtitle` fold into `PageContainer`. `.app-*` (`.app-topbar`, `.app-sidebar`, `.app-nav-rail`, …) turned out to be **AppShell's own** class prefix, not a consumer/demo class — a fourth convention for the same component.
4. **Two things don't attribute to any single component** and are reported separately, not folded into an arbitrary one: `.ui-control*` (shared base under Input/Select/Textarea/…) and `.ui-choice-*` (shared base under Checkbox/Radio). `.ui-chart`/`.ui-chart-trend-*` (the ChartFrame wrapper shared by Area/Bar/Line/PieChart) likewise. **`.ui-combobox-*` (24 declarations, `src/styles/control.css`) matches no render call anywhere in `src/components` — it appears to be dead CSS**, a separate finding from theme-reachability and flagged as such, not counted toward any component's score.
5. **Classified each declaration**: `reachable` if its value contains `var(--x)` and `--x ∈ agent/tokens.json`; `hardcoded-internal-token` if it contains `var(--x)` but `--x` is _not_ published (counted as hard-coded per the brief: _"a value that is var(--x) where --x is an INTERNAL, undocumented custom property is hard-coded from the consumer's point of view"_); `hardcoded-literal` if there is no `var()` at all.
6. **Structural exclusions** — narrow, mechanical, and named per row so a reviewer can disagree with any one of them:
   - `border(-*)-width: 0/1px/2px/thin/medium` — hairline/reset, not a colour or scale decision.
   - `opacity: 0` or `1` — binary show/hide toggle, not a translucency value (`opacity: 0.5`, `0.6`, `0.7`, `0.38`… are all still counted as hard-coded — those _are_ a design decision).
   - `padding*`/`margin*`/`gap: 0` — box-model reset, and `padding`/`margin: auto` — the centering idiom.
   - `min-(width|height|inline-size|block-size): 0/auto` — the flexbox/grid overflow-fix idiom.
   - `box-shadow: none` / `backdrop-filter: none` — removes the effect entirely, nothing to retune.
   - `color`/`background`/`border`/`box-shadow: transparent | inherit | currentColor | none | initial | unset` — the value defers to context and paints nothing of its own; there is no authored colour for a theme to override.
   - `color`/`background`/`border` set to a **forced-colors/high-contrast system keyword** (`CanvasText`, `Highlight`, `ButtonText`, …) — deliberately not themeable; it defers to the _user's OS_ palette, and overriding it would be an accessibility regression, not a fix.
   - Anything else — including `border-radius: 0`, `font-weight: 700`, and disabled-state opacities — is **counted as hard-coded**, on purpose: a tenant that sets `borderRadius: 0` globally, or wants sharp corners, or a different disabled-state fade, is a real theming request these values would resist.
7. **The published-token cross-check (Finding 1, below) surfaced a second-order pattern**: several `hardcoded-internal-token` hits are _local variant-switch indirection_ — e.g. `inline-size: var(--avatar-glyph-size)` where `--avatar-glyph-size` is itself set per-size by `--avatar-glyph-size: var(--avatar-glyph-size-xs)` one selector up, and `--avatar-glyph-size-xs` **is** published. Per the brief's rule this is still counted as hard-coded (the name written at the point of use is not itself a published, stable knob), but it is a materially different, and much less serious, defect than a value with no path to a published token at all — so the two are told apart below rather than blended into one number.

## The Ant Design layer question

Ant Design v5: **Seed → Map → Alias → Component**. A Seed is a handful of raw decisions (a brand hue, a base radius, a base font size). Map derives an _algorithmic scale_ from the Seed (e.g. `radius100`, `radius200`, `radiusLG`) — internal, not meant to be hand-edited. Alias assigns _semantic_ names to slices of the Map for reuse across components (`colorPrimary`, `colorBorder`). Component tokens are the last word a specific component reads (`Button.colorPrimary`), usually itself derived from an Alias.

This library has three of the four, cleanly separated in `agent/tokens.json`: **`foundation` (201 tokens)** plays Seed (`--background`, `--radius`, `--radius-ratio`, `--font-size-base`…), **`semantic` (92)** is Alias (`--primary`, `--border`, `--muted-foreground`…), **`component` (1,688)** is Component, and the chain resolves correctly in the overwhelming majority of cases — 943 of the 1,688 component tokens (56%) reference another custom property rather than bottoming out in a literal, and of the 745 that do bottom out at a literal, only **6** are colours (mostly QR-code black/white and two brand-identity marks, both legitimately fixed-by-design, plus two on `Upload`'s avatar-change overlay, `rgb(0 0 0 / 0.7)` and `#fff`, which are not — see Finding 2).

**Finding 1 — the Map layer exists in code and is invisible to the catalog, because it lives in the wrong directory.** `src/styles/base.css:169-176` derives a φ-ratio radius scale — `--radius-xs`, `--radius-sm`, `--radius-md`, `--radius-lg`, `--radius-xl`, `--radius-2xl` — algorithmically from the Seed (`calc(var(--radius) / var(--radius-ratio))`, etc.), exactly Ant Design's Map tier. The catalog generator, `scripts/gen-agent-catalog.mjs:137-142`, only scans `src/tokens/foundation.css`, `src/tokens/derived.css`, `src/tokens/semantic/*.css`, and `src/tokens/components/*.css` — it never looks at `src/styles/`. So `--radius-md` is real, load-bearing (referenced by **40 separate `border-radius` declarations** across Badge, Table, Dialog, Segmented, Tabs, Mega Menu, Time Picker, Tree Select, Calendar, Transfer, Skeleton, Code Block, Prose, App Launcher, Upload, Steps, Menu, Draggable Panel, Float Button, Descriptions, Chart), and is one `var()` hop from two published Seed tokens (`--radius`, `--radius-ratio`) — but a consumer reading `agent/tokens.json` cannot find `--radius-md` by name, and an agent using `get_tokens` would not know it exists. This is a location bug in the generator's scan list, not a design decision: the equivalent scales for spacing (`--space-*`) and type (`--font-size-*`) **are** published, so the pattern the repo intends is clearly "publish the Map." Fix is mechanical — move the scale into `src/tokens/foundation.css`, or add `src/styles/base.css` to the generator's scan list — and it would flip all 40 of those declarations, plus a same-shaped (unquantified here) `--text-2xs`…`--text-5xl` bridge scale at `base.css:213-244`, from "hard-coded" to "reachable" in one PR, with no CSS behaviour change.

**No missing layer otherwise** — Seed, Alias and Component are each real, populated, and (component tokens) individually overridable per the framework's own theming docs. The gap is narrower than "no Map tier"; it is "one Map-tier scale published, one not," and it is fixable at the generator, not by inventing new terminology.
